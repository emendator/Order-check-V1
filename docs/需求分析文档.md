# 订单查重系统 — 需求分析文档

> 版本: v1.0  
> 日期: 2026-07-14  
> 状态: 初始分析

---

## 一、项目背景与目标

### 1.1 项目背景

业务场景中，用户需要从多个来源（如电商平台导出、物流系统导出等）获取包含订单信息的表格文件。这些表格中的订单可能存在重复发货的风险——即同一收件人的姓名、地址、电话完全一致，但被多次录入发货系统。

### 1.2 核心目标

构建一个 **订单查重管理系统**，实现：

- 表格数据自动导入与解析
- 基于"姓名 + 地址 + 电话"三重匹配的重复订单检测
- 醒目地提醒用户潜在重复发货风险
- 数据自动过期清理（3天TTL）

## 二、功能需求详述

### 2.1 表格上传与解析（Upload & Parse）

| 项目 | 说明 |
|------|------|
| 支持格式 | `.xlsx`、`.xls`、`.csv` |
| 上传方式 | 前端拖拽/点击上传 |
| 表头识别 | **模糊匹配** 姓名、地址、电话三列 |
| 模糊匹配规则 | 见下方 2.1.1 节 |
| 批量处理 | 支持一个表格包含多条订单记录 |

#### 2.1.1 表头模糊匹配规则

上传的表格表头命名可能不统一，系统需支持以下常见变体的自动识别：

**姓名列（匹配任一即认为命中）：**

- `姓名`、`名字`、`收件人`、`收货人`、`收货姓名`、`联系人`、`客户姓名`、`客户名称`
- `name`、`customer_name`、`receiver`、`contact_name`、`recipient`
- 包含以上关键词的列名（如"收货人姓名"、"客户姓名（必填）"）

**地址列（匹配任一即认为命中）：**

- `地址`、`收货地址`、`收件地址`、`详细地址`、`联系地址`、`配送地址`、`邮寄地址`
- `address`、`shipping_address`、`delivery_address`、`addr`、`location`
- 包含以上关键词的列名

**电话列（匹配任一即认为命中）：**

- `电话`、`手机`、`手机号`、`联系电话`、`联系方式`、`收货电话`、`手机号码`、`电话号码`、`Tel`
- `phone`、`mobile`、`tel`、`telephone`、`contact_number`、`cell`
- 包含以上关键词的列名

> **匹配策略**: 大小写不敏感，去除空格后进行包含匹配。若多个列同时匹配同一类别（如既有"姓名"又有"收件人"），优先选择精确匹配度最高的列；若无法判定，提示用户手动选择。

#### 2.1.2 列匹配失败处理

- 若三列中有任何一列无法匹配，前端弹出提示，列出已匹配和未匹配的列
- 允许用户手动从下拉框中选择对应的列

### 2.2 重复检测（Duplicate Detection）

#### 2.2.1 检测规则

当新一批数据导入时，系统自动执行以下检查：

```
SELECT 记录 WHERE 
  姓名 = 新记录.姓名 
  AND 地址 = 新记录.地址 
  AND 电话 = 新记录.电话
```

- 三个字段**完全相等**（去除首尾空格、统一全角/半角后比较）
- 检测范围：数据库中**所有未过期**的记录
- 检测时机：**每次上传新表格后立即执行**

#### 2.2.2 提示机制

- 若检测到重复，前端弹出**醒目警告**（红色/橙色高亮横幅或模态框）
- 警告文案：**"⚠️ 发现重复订单！以下订单的姓名、地址、电话与数据库中已有记录完全一致，请检查是否重复发货。"**
- 列出所有冲突记录的详细信息（表格形式展示）
- 用户可确认"已知晓"关闭提示，但数据仍正常入库（不阻止入库，只做提醒）

### 2.3 数据生命周期管理（Data TTL）

| 项目 | 说明 |
|------|------|
| TTL 时长 | **3天（72小时）** 从上传输时间起算 |
| 过期处理 | 后台定时任务自动清理过期数据 |
| 清理频率 | 每小时检查一次 |
| 前端展示 | 每条记录显示"剩余时间"倒计时 |
| 倒计时格式 | "剩余 X天 X小时 X分钟" 或 "剩余 X小时" |

### 2.4 数据库管理界面（CRUD）

前端提供简洁的数据管理界面：

| 功能 | 说明 |
|------|------|
| **查（Read）** | 分页表格展示所有未过期记录；支持按姓名/电话关键字搜索 |
| **增（Create）** | 手动新增一条记录（姓名+地址+电话表单） |
| **改（Update）** | 点击编辑，修改已有记录的字段 |
| **删（Delete）** | 单条删除 或 批量勾选删除；删除前二次确认 |
| **刷新** | 手动刷新数据列表 |

## 三、非功能需求

### 3.1 性能

- 单次上传支持 ≤ 10,000 条记录
- 重复检测查询应在 2 秒内完成
- 前端列表分页加载，每页 20-50 条

### 3.2 可用性

- 界面简约高效，减少不必要的操作步骤
- 关键操作（删除、重复警告）有明确的视觉反馈
- 支持键盘快捷操作（如回车提交）

### 3.3 数据安全

- 姓名、地址、电话属于敏感信息，数据库文件应妥善保管
- 前端不缓存敏感数据到 localStorage

### 3.4 兼容性

- 支持主流现代浏览器（Chrome, Edge, Firefox 最新版）
- 后端运行于 Windows 环境

## 六、数据库表设计（当前版本）

### 6.1 订单记录表 `orders`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增主键 |
| name | TEXT NOT NULL | 姓名 |
| address | TEXT NOT NULL | 地址 |
| phone | TEXT NOT NULL | 电话 |
| product_model | TEXT DEFAULT '' | 产品型号 |
| batch_id | TEXT | 批次标识（同一表格上传） |
| filename | TEXT | 来源文件名 |
| shipped | BOOLEAN DEFAULT 0 | 是否已发货 |
| processed | BOOLEAN DEFAULT 0 | 是否已处理（重复审查后标记） |
| created_at | DATETIME | 录入时间 |
| expire_at | DATETIME | 过期时间（created_at + 3天） |

### 6.2 重复检测规则

重复判定依据：**姓名 + 地址 + 电话 + 产品型号** 四者完全一致（去除首尾空格、统一全角/半角后比较）。
已标记为"已处理"的记录不参与重复检测。

### 6.3 重复处理流程

1. 系统对导入的新数据自动进行四重匹配检测
2. 发现重复时，前端醒目告警
3. 用户进入"重复审查"模式，查看所有重复组
4. 每个重复组中所有记录一同展示，用户选中一条保留，其余标记为"已处理"
5. 已处理的记录仍保留在数据库中，但不再参与后续重复审查
6. 数据仍然按导入日期 3 天后过期自动清理

### 6.2 索引

```sql
CREATE INDEX idx_orders_name_address_phone ON orders(name, address, phone);
CREATE INDEX idx_orders_expire_at ON orders(expire_at);
```

## 七、风险与待确认事项

1. ⚠️ **三字段完全相同** 是否足以判定重复？是否需要增加其他维度（如订单号、商品名称）？
2. ⚠️ 重复检测是仅提醒还是**阻止入库**？当前方案：提醒但不阻止。
3. ⚠️ 3天TTL是否可配置？当前方案：硬编码3天，后续可改为可配置。
4. ⚠️ 是否需要导出功能？当前方案：暂不包含。
