# 订单查重系统 — 登录与权限系统 需求分析文档

> 版本: v1.0
> 日期: 2026-08-06
> 状态: ✅ 已全部实现并通过测试（2026-08-06）
> 关联项目: 订单查重系统（React + FastAPI + SQLite）

---

## 一、项目背景与目标

### 1.1 背景

订单查重系统目前为**无登录、单用户**使用模式。业务需要扩展为**多用户、多公司、分级权限**的企业级使用模式：

- 每个账户维护**自己的订单库**，账户之间互不影响
- 系统分为**三级权限**：最高级管理员（超级管理员）> 管理员 > 用户
- 通过**邀请码**机制控制注册入口，防止无关人员注册
- 通过**有效时间**机制控制账号生命周期

### 1.2 核心目标

1. 提供登录 / 注册界面（美观大气简约）
2. 实现三级权限体系与账号管理
3. 实现邀请码分发与一次性作废机制
4. 实现公司（加入 / 创建 / 改密码）体系
5. 实现订单库按账户隔离
6. 实现账号有效期管理（到期禁止登录、提醒、清除、延长、级联删除）

## 二、角色与权限体系

### 2.1 三级角色

| 角色 | 英文标识 | 说明 |
| ------ | --------- | ------ |
| 最高级管理员 | `super_admin` | 系统拥有者，仅一人（用户名 `admin`） |
| 管理员 | `admin` | 通过一级邀请码注册，可管理本公司及下辖用户 |
| 用户 | `user` | 通过二级邀请码注册，仅能使用订单功能 |

### 2.2 权限矩阵

| 功能 | 超级管理员 | 管理员 | 用户 |
| ------ | :---: | :---: | :---: |
| 登录 / 退出 | ✅ | ✅ | ✅ |
| 修改自己的登录密码 | ✅ | ✅ | ✅ |
| 订单库（上传/查重/CRUD，仅自己的数据） | ✅ | ✅ | ✅ |
| 注册后选择加入或创建公司 | ✅（预置） | ✅（注册后一次） | ❌（仅加入） |
| 修改本公司密码 | ✅ | ✅ | ❌ |
| 分发一级邀请码（→管理员） | ✅ | ❌ | ❌ |
| 分发二级邀请码（→用户） | ✅ | ✅ | ❌ |
| 用户管理界面（邀请码+账号管理） | ✅ | ✅ | ❌ |
| 延长账号有效时间 | ✅ | ✅ | ❌ |
| 清除到期账号 | ✅ | ✅ | ❌ |
| 清除管理员（级联清除其下用户） | ✅ | ❌ | ❌ |

> **管理范围定义**（超级管理员与管理员统一）：
>
> - 用户管理界面**仅显示本账户 + 本账户分发的邀请码所注册的账户**（不包含他人邀请的账户）
> - 判定归属：`账户.注册邀请码.created_by == 当前登录账户.id`
> - 超级管理员清除管理员时，级联清除该管理员分发的邀请码所注册的用户（基于邀请码链）

## 三、功能需求详述

### 3.1 登录

| 项目 | 说明 |
| ------ | ------ |
| 登录方式 | 用户名 + 密码 |
| 密码校验 | 与数据库中哈希值比对（加密存储，见 §6 安全设计） |
| 成功响应 | 返回 token + 用户信息（用户名、角色、公司名、剩余有效天数等） |
| 失败处理 | 统一提示"用户名或密码错误"（不暴露具体原因，防探测） |
| 特殊状态拦截 | 见 3.7 账号有效期机制 |

### 3.2 注册

| 项目 | 说明 |
| ------ | ------ |
| 必填字段 | 用户名、密码、邮箱、邀请码 |
| 用户名 | 全局唯一；建议 3-20 位，字母/数字/下划线 |
| 密码 | 6 位以上；加密存储 |
| 邮箱 | 全局唯一；格式校验（正则，不引入第三方库）；仅作为账号绑定信息 |
| 邀请码 | 必填；校验有效性（未使用、未过期、未被作废） |
| 角色判定 | **一级邀请码** → 注册为管理员；**二级邀请码** → 注册为用户 |
| 邀请码消耗 | 注册成功后该邀请码记录**自动删除**（一次性），不可复用；邀请关系固化在用户表的 `invited_by` 字段，可追溯 |
| 有效时间 | 新账号 `valid_until` 继承所使用邀请码的 `valid_until` |
| 注册后状态 | `pending_company`（尚未绑定公司），不可登录，必须完成公司设置（§3.3） |

### 3.3 公司体系

#### 3.3.1 公司绑定流程

注册账号（已通过邀请码验证）后，进入公司设置步骤：

| 角色 | 可选操作 |
|------|---------|
| 管理员 | **加入公司** 或 **创建新公司**（二选一） |
| 用户 | 仅 **加入公司** |

- **加入公司**：输入`公司名称` + `公司密码` → 校验通过后绑定到该公司
- **创建新公司**：输入`公司名称` + 设置`公司密码` → 创建新公司并绑定

#### 3.3.2 公司规则

| 规则 | 说明 |
| ------ | ------ |
| 公司名称 | 全局唯一；**填写后不可修改**（注册/创建时前端明确提示"公司名称提交后不可修改"） |
| 公司密码 | 加密存储（同用户密码哈希方式） |
| 修改公司密码 | 仅本公司**管理员及以上**可修改（需要旧密码验证）；用户不可修改 |
| 一个公司 | 可容纳多个管理员、多个用户 |
| 公司自动删除 | 公司下**没有任何账号**时自动删除（删除最后一个账号时触发；定时任务每小时兜底清理） |

> **典型场景**：新管理员选择"加入公司"，输入`我的公司` + 公司密码 `123123` 即可加入总部公司；也可另建分公司。

### 3.4 预置数据（Seed）

系统初始化时自动创建：

| 类型 | 数据 |
| ------ | ------ |
| 超级管理员 | 用户名 `admin`，密码 `123123`，邮箱 `admin@example.com`（可自定义），角色 `super_admin` |
| 公司 | 名称 `我的公司`，密码 `123123`，创建人 = 超级管理员 |
| 有效期 | 超级管理员 `valid_until = NULL`（**永久有效**，不可被清除） |
| 游客账号 | 用户名 `guest`，`is_guest = True`，角色 `user`，密码随机（不可登录），邮箱 `guest@guest.local`，永久有效，无公司 |

### 3.5 邀请码体系

#### 3.5.1 邀请码属性

| 字段 | 说明 |
| ------ | ------ |
| 邀请码 | 随机字符串（如 `secrets.token_urlsafe(6)` 生成），全局唯一 |
| 级别 | `1` = 一级（注册管理员）；`2` = 二级（注册用户） |
| 分发者 | `created_by`，记录分发者账号 |
| 有效时间 | `valid_until`，分发时由分发者设置 |
| 状态 | `unused`（未使用）/ `revoked`（被分发者作废）；**已使用的邀请码注册后自动删除**，不保留记录 |
| 一次性 | 使用后立即删除记录，不可再次使用 |

#### 3.5.2 分发权限

| 分发者 | 一级邀请码 | 二级邀请码 |
| -------- | :---: | :---: |
| 超级管理员 | ✅ | ✅ |
| 管理员 | ❌ | ✅ |
| 用户 | ❌ | ❌ |

### 3.6 订单库隔离

- `orders` 表增加 `owner_id` 字段（关联 `users.id`）
- **所有订单接口**（查询、新增、编辑、删除、查重、导入、文件名等）均以当前登录用户的 `id` 过滤，仅操作自己的数据
- 账户之间互不可见、互不影响
- 旧数据迁移策略：上线时把历史订单（`owner_id IS NULL`）**统一划归超级管理员**，避免数据丢失

### 3.7 账号有效期机制

#### 3.7.1 有效期设置

- 分发邀请码时设置有效时间（`valid_until`）
- 使用邀请码注册的账号自动继承该时间
- 超级管理员永久有效

#### 3.7.2 到期处理

| 环节 | 行为 |
| ------ | ------ |
| 定时任务 | 每小时扫描：`valid_until <= now` 的账号 → `status = expired` |
| 登录校验 | 登录时双重检查 `status != expired` 且 `valid_until > now`，否则拒绝登录并提示 |
| 前端提醒 | 登录成功且剩余有效天数 ≤ 7 天时，顶部横幅提醒"账号将于 X 天后到期，请联系管理员延长"；已到期登录失败时明确提示"账号已到期，请联系管理员" |

#### 3.7.3 管理操作（用户管理界面）

| 操作 | 说明 |
| ------ | ------ |
| 延长有效时间 | 选择账号 → 设置新的有效时间（默认建议当前时间 + N 天） |
| 清除到期账号 | 删除账号（含其订单数据、其分发的邀请码）；仅限管理范围内的到期/过期账号 |
| 禁用/启用 | 可选能力，用于临时封禁（本期列为可选） |

#### 3.7.4 级联清除（仅超级管理员）

超级管理员清除**管理员**账号时：

1. 找到该管理员**分发的所有二级邀请码**
2. 找到通过这些邀请码注册的**所有用户账号**（包括这些用户的订单数据）
3. **同步全部删除**
4. 删除该管理员账号本身、其订单数据、其分发的所有邀请码（含未使用的）

> 注意：**不删除公司**（公司可能还有其他管理员/用户）。被级联清除的账号通过登录时 `username not found` 自然失效。

### 3.8 游客模式（免密体验）

#### 3.8.1 入口与流程

- 登录页登录 Tab 下方提供 **"以游客身份登录"** 按钮（带警示提示：不会保留任何数据，退出登录后将自动清除所有使用痕迹）
- 点击后调用 `POST /api/auth/guest-login`，无需账号密码，直接以游客身份进入系统

#### 3.8.2 游客权限

| 能力 | 说明 |
| ------ | ------ |
| 订单功能（上传/查重/CRUD） | ✅ 与普通用户一致，仅操作自己的数据 |
| 用户管理界面 | ❌（游客角色为 `user`，无管理入口） |
| 邀请码、公司、账号管理 | ❌ |
| 公司信息 | 无（`company_id = NULL`，不显示公司标签） |

#### 3.8.3 数据不保留机制

| 环节 | 行为 |
| ------ | ------ |
| 数据归属 | 游客创建的订单归属固定游客账号（`owner_id = guest.id`），与正常账号隔离 |
| 退出清除 | 游客退出登录时**立即删除其全部订单**并清除 token（`POST /api/auth/logout` 中 `is_guest` 分支） |
| 定时兜底 | 定时任务每小时执行 `cleanup_guest_data`：若游客未登录（token 为空）则清理其残留订单 |
| 前端提醒 | 登录页警示 + Dashboard 顶部横幅（游客模式不会保留数据） |

#### 3.8.4 角色显示

- 游客账号数据库角色为 `user`（保证无管理权限），但前端 Dashboard 角色标签显示为 **"游客"**（紫色）而非"用户"

## 五、API 设计

> 统一响应格式沿用现有：`{ success, data, message }`。
> 除登录/注册/公司设置/健康检查外，均需携带 `Authorization: Bearer <token>`。

### 5.1 认证模块 `/api/auth`

| 方法 | 路径 | 权限 | 说明 |
| ------ | ------ | ------ | ------ |
| POST | `/api/auth/register` | 公开 | 注册：`{username, password, email, invite_code}` → 校验邀请码 → 创建账号（role 由邀请码级别决定，status=`pending_company`）→ 返回 `{need_company: true, role}` |
| POST | `/api/auth/company-setup` | 登录(pending) | 公司设置：`{action: "join"\|"create", company_name, company_password}` → 绑定公司 → 返回 `{token, user}`（即完成注册登录） |
| POST | `/api/auth/login` | 公开 | 登录：`{username, password}` → 校验有效期/状态 → 返回 `{token, user}`（含 `days_left`） |
| POST | `/api/auth/guest-login` | 公开 | 游客登录：免账号密码 → 生成新 token → 返回 `{token, user}`（`is_guest=true`） |
| POST | `/api/auth/logout` | 登录 | 登出：清除当前 token；**游客退出时同时删除其全部订单** |
| GET | `/api/auth/me` | 登录 | 当前用户信息（含剩余天数、公司名） |
| PUT | `/api/auth/password` | 登录 | 修改自己的登录密码：`{old_password, new_password}` |

### 5.2 公司模块 `/api/companies`

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/companies/check?name=xxx` | 登录 | 检查公司名是否存在（前端注册/创建时提示用） |
| PUT | `/api/companies/password` | admin/super_admin | 修改本公司密码：`{old_password, new_password}` |

### 5.3 邀请码模块 `/api/invite-codes`

| 方法 | 路径 | 权限 | 说明 |
| ------ | ------ | ------ | ------ |
| POST | `/api/invite-codes` | super_admin / admin | 分发：`{level, valid_until}`；super_admin 可 level=1/2，admin 仅 level=2 |
| GET | `/api/invite-codes` | super_admin / admin | 我分发的邀请码列表（含状态、使用者、使用时间） |
| DELETE | `/api/invite-codes/{id}` | 分发者 | 作废未使用的邀请码（仅 own 的） |

### 5.4 用户管理模块 `/api/admin/users`

| 方法 | 路径 | 权限 | 说明 |
| ------ | ------ | ------ | ------ |
| GET | `/api/admin/users` | super_admin / admin | 账号列表（仅本账户 + 本账户邀请码注册的账户）含注册时间、最后登录、有效时间、状态 |
| PUT | `/api/admin/users/{id}/extend` | 管理范围内 | 延长有效时间：`{valid_until}` |
| DELETE | `/api/admin/users/{id}` | 管理范围内 | 清除账号；super_admin 清 admin 时级联清除其下用户（含订单数据、邀请码） |

### 5.5 订单模块（改造）

现有全部订单接口增加当前用户过滤：

- `GET /api/orders`、`GET /api/orders/{id}` → `WHERE owner_id = 当前用户`
- `POST /api/orders`、`PUT /api/orders/{id}`、`DELETE /api/orders/{id}` → 校验归属 + `owner_id = 当前用户`
- `POST /api/orders/batch-delete`、`batch-process`、`process-duplicate-group`、`delete-by-filename` → 同上
- `POST /api/upload/preview`、`/import`、`/batch-import` → 入库记录 `owner_id = 当前用户`
- `GET /api/orders/duplicates`、`/filenames` → 同上

## 六、安全设计

### 6.1 密码加密存储（核心要求）

- **方案**：`hashlib.pbkdf2_hmac('sha256', password, salt, iterations=100_000)`，随机 16 字节盐，存储格式 `pbkdf2$100000$<salt_hex>$<hash_hex>`
- **优点**：Python 标准库实现，**零新增依赖**，无 passlib/bcrypt 版本兼容坑，安全性满足内部系统要求
- 用户登录密码、公司密码均使用同一套哈希函数

### 6.2 会话 Token

- **方案**：Session Token（`secrets.token_urlsafe(32)`），存于 `users.token` 字段，登录时生成、登出/清除账号时置空
- **优点**：零新增依赖；天然支持"禁用即失效"（清除 token 即可），无需 JWT 黑名单
- **备选**（如需无状态）：`PyJWT` + HS256，但会新增依赖且无法主动失效，不推荐本场景
- 前端将 token 存 `localStorage`，请求头携带 `Authorization: Bearer <token>`

### 6.3 其他安全要点

- 邮箱格式：正则校验（零依赖）
- 邀请码：`secrets.token_urlsafe(6)` 生成
- 权限校验：FastAPI 依赖注入 `get_current_user` + `require_role(...)`，所有受保护接口统一挂载
- 登录失败不区分"用户不存在/密码错误"
- 输入长度/格式限制（用户名 3-20 位、密码 ≥6 位、邮箱 ≤200）
- 敏感信息（密码哈希、token）不出现在任何接口返回体中

## 七、前端页面设计

> 风格要求：**美观、大气、简约**。Ant Design 5 + 现有主题（主色 `#1677ff`），卡片式布局 + 渐变/纯色背景。

### 7.1 页面清单与状态机

```
未登录 ──登录页──▶ 已登录(pending_company) ──公司设置页──▶ 已登录(active)
                          ▲                                    │
                          └────────────── 退出登录 ◀────────────┘
```

| 页面 | 路由/状态 | 说明 |
| ------ | ---------- | ------ |
| 登录页 | 未登录 | 含"登录 / 注册"切换 |
| 公司设置页 | pending_company | 管理员：加入/创建二选一；用户：仅加入 |
| 主界面 | 已登录 | 现有 Dashboard + 顶部用户信息/退出 |
| 用户管理页 | 已登录且 admin/super_admin | 邀请码管理 + 账号管理 |

> 路由方案：本项目当前无 react-router。**推荐保持零依赖**，用 `AuthContext` + 页面状态机（`view` 状态）切换，避免引入 react-router。

### 7.2 登录页

- 居中卡片，标题"订单查重管理系统"+ 副标题
- 背景：柔和渐变（如深蓝 → 靛蓝）或浅色极简风
- 表单：用户名、密码、登录按钮；下方"没有账号？注册"
- 回车提交；loading 态；错误用 message 提示

### 7.3 注册页

- 字段：用户名、密码、确认密码、邮箱、邀请码
- 校验：两次密码一致、格式校验
- 提交成功后：若为一级邀请码（管理员）→ 跳转公司设置页；二级邀请码（用户）→ 同样跳公司设置页（仅加入模式）
- 邀请码输入框旁可提示"邀请码请联系管理员获取"

### 7.4 公司设置页

- 卡片标题"设置公司信息"
- 管理员：两个选项卡片（加入公司 / 创建新公司），选中后切换表单
  - 加入：公司名称 + 公司密码（失焦/输入时校验公司是否存在）
  - 创建：公司名称 + 设置公司密码；**明显提示"公司名称提交后不可修改"**
- 用户：仅"加入公司"表单
- 提交成功 → 自动登录进入主界面

### 7.5 主界面改造（Dashboard）

- Header 右侧：显示 `用户名 / 角色标签 / 公司名` + 退出登录按钮
- 管理员/超级管理员：Header 或侧栏增加"用户管理"入口
- 剩余有效天数 ≤ 7 天：顶部 Alert 横幅提醒
- 401 响应 → 自动登出回登录页

### 7.6 用户管理页

**Tab 1：邀请码管理**

- 按钮"分发邀请码"（弹窗：级别下拉（按权限过滤）、有效时间日期选择器）
- 表格：邀请码、级别、状态、有效期、使用者、使用时间、创建时间
- 操作：作废（仅未使用）

**Tab 2：账号管理**

- 表格：用户名、角色、公司、状态、注册时间、最后登录时间、有效截止时间
- 操作：延长有效期（弹窗选择新时间）、清除账号（二次确认，提示级联影响）
- 超级管理员界面额外显示"清除管理员将级联删除其下用户"

## 九、边界情况与设计决策记录

| # | 场景 | 决策 |
| --- | ------ | ------ |
| 1 | 用户注册用了一级邀请码？ | 不允许：邀请码级别决定角色，一级→管理员、二级→用户，级别不匹配则报错 |
| 2 | 邀请码已使用/过期/作废 | 注册直接拒绝，提示"邀请码无效" |
| 3 | 管理员清除自己 | 禁止（不可自删） |
| 4 | 清除超级管理员 | 禁止（admin 不可被清除，系统永远保留） |
| 5 | 管理员清除用户时是否级联其下级 | 用户无下级，不涉及；仅超级管理员清管理员时级联 |
| 6 | 历史订单数据归属 | 迁移时全部划归超级管理员 |
| 7 | pending_company 账号能否登录 | 不能；登录接口拒绝并提示"请先完成公司设置" |
| 8 | 公司重名 | 创建/加入前校验唯一性 |
| 9 | 用户能否改公司密码 | 不能，仅管理员及以上 |
| 10 | 延长有效期是否可以提前/缩短 | 允许，管理员可自由设置新截止时间 |
| 11 | 到期账号数据是否立即删除 | 否，仅置 `expired` 禁登；由管理员手动清除或后续扩展自动清理 |
| 12 | 是否支持密码找回 | 本期不做（邮箱仅绑定用途），后续可扩展 |

## 十、验收标准（Done Definition）

1. 无登录访问任何订单接口 → 401
2. 用 `admin/123123` 可登录，且公司为"我的公司"
3. 超级管理员可分发一级、二级邀请码；管理员仅可分发二级
4. 一级邀请码注册 → 管理员，可"加入或创建公司"；二级邀请码注册 → 用户，仅"加入公司"
5. 邀请码使用一次后失效，不可复用
6. 数据库中的密码/公司密码均为哈希，无明文
7. 两个不同账户各自上传订单互不可见
8. 分发邀请码设置有效期后，注册账号继承；到期后禁止登录并提示
9. 管理员/超级管理员可在用户管理界面延长有效时间、清除到期账号
10. 超级管理员清除管理员 → 其下用户账号同步被清除
11. 公司名称不可修改；管理员可修改公司密码
12. 前端登录/注册/公司设置页面美观大气简约，TypeScript 编译通过
